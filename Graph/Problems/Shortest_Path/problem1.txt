Cross-District Courier Run

A same-day courier company has been asked to move a sealed package from one neighborhood hub to another while avoiding unnecessary detours. The city map is not drawn as a simple street grid. Instead, it is represented as a network of intersections, service lanes, overpasses, and narrow connectors, each with its own travel cost. Some roads are short but difficult to use at rush hour. Others are longer yet easier to traverse because they bypass traffic lights or restricted turns. The dispatcher is not interested in exploring the whole city. The only thing that matters is getting from the designated start hub to the designated destination hub with the least possible cumulative cost.

The route must respect the available connections exactly as they appear in the network. If two points are not directly linked, the courier cannot invent a new road between them. The vehicle may pass through intermediate hubs if that helps lower the overall cost, but the final answer should reflect the cheapest complete travel plan from the start to the destination, not merely the first route that looks convenient. A route with more steps can still be better if it uses cheaper edges, while a route with fewer steps can be worse if one of its segments is expensive.

Several practical details appear in the dispatch notes. The courier begins loaded, so every unnecessary kilometer matters. The package is fragile, so the route should be efficient enough to avoid delays, even though the actual challenge is purely on paper and no timing simulation is required. There is no need to visit every location in the network, and there is no requirement to return to the starting point. The goal is simply to determine the least costly way to travel from the origin node to the destination node using the weighted connections provided by the graph.

Because the network may include misleading shortcuts and a mix of high-cost and low-cost transitions, the intended solution should compute a globally optimal path rather than rely on local intuition. The output should therefore support a clean decision about which sequence of connected nodes minimizes the total travel weight between the two specified endpoints.

The city planners who maintain the road network also want the answer to be explainable after the fact. In their reports, a route is more useful when it can be justified as the cheapest complete transfer rather than as a lucky guess that happened to work. That is why the graph must be treated as a weighted system where every available connection can influence the final total. A direct edge may be tempting, but if it forces the rest of the trip onto expensive roads, it is not necessarily the best choice. Likewise, a route with an extra intermediate hub can still win if that detour unlocks a cheaper overall path.

For the courier company, this is exactly the kind of question that comes up when the night shift is trying to keep delivery promises without wasting fuel. The network is not searched because every road is interesting; it is searched because the origin and destination are fixed, and the shortest practical transfer matters more than any other property. The result should therefore describe the cheapest valid path through the weighted graph, including any useful intermediate hubs that make the final cost smaller.
